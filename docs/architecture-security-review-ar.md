# مراجعة معمارية وأمنية لتطبيق NetCraft

**التاريخ:** 25 أكتوبر 2026  
**النطاق:** التطبيق كاملًا، بالاستناد إلى مهارتي `android-architecture-clean` و`android-security-best-practices`. سياسة البناء الحالية v6-only؛ لا يُسمح باتصال RouterOS v7.
**طريقة المراجعة:** فحص ساكن للمصدر والـManifest وإعدادات التخزين/الشبكة، واختبارات الوحدة وLint. لم يُجرَ اتصال براوتر فعلي أو اختبار اختراق خارجي.

## التصميم الحالي

المشروع تطبيق Android أحادي الوحدة (`:app`) يستخدم Kotlin وJetpack Compose وRoom وCoroutines/Flow. واجهة Compose موجودة في `com.example.ui.screens`، وتتصل غالبًا بـ`MikroTikViewModel`، ثم بـ`MikroTikRepository` الذي يدير اتصال RouterOS Binary API المدعوم، واكتشاف الإصدار، وأوامر User Manager/Hotspot، وعمليات الصيانة، والتخزين المؤقت والسجل التشغيلي. أزيل عميل REST من `MikroTikRepository` بالكامل، ولم تعد أي عملية Hotspot أو إعادة تشغيل/إيقاف أو مزامنة تستخدم HTTP. بقيت بعض فروع fallback داخل منطق User Manager كشيفرة غير قابلة للوصول لأن بوابة الإصدار ترفض أي جلسة غير v6؛ ويلزم حذفها في تنظيف لاحق منفصل. `MikroTikNativeApi` و`RouterFtpClient` و`AiDoctorClient` عملاء نقل منفصلون جزئيًا، بينما تحتوي DAOs والكيانات في `data/local` على التخزين.

الحدود موجودة وظيفيًا لكنها ليست Clean Architecture مكتملة: لا توجد وحدة أو حزمة `domain` مستقلة أو عقود Repository وUse Cases تفصل قواعد العمل عن Android/Room/النقل. `MikroTikRepository` و`MikroTikViewModel` كبيران، والـViewModel يعرّف المستودع مباشرة. يوجد أيضًا مساران لحزم ViewModel (`com.example.viewmodel` و`com.example.ui.viewmodel`)، مما يزيد تشتت الملكية. هذا وصف للحالة الراهنة، وليس سببًا لاقتلاع التطبيق أو إعادة كتابته.

## التصميم المستهدف

اعتماد حدود تدريجية داخل الوحدة الحالية أولًا، من دون تقسيم Gradle modules قبل ثبوت الحاجة:

```text
Compose screens
  └─ Screen state / ViewModel (StateFlow + lifecycle-aware collection)
       └─ domain use cases + domain models
            └─ repository contracts
                 └─ data implementations
                       ├─ RouterOS v6 native API / FTP clients
                      ├─ Room DAOs and local preferences
                      └─ AI provider client
```

تبقى أوامر RouterOS، اختيار المسار المدعوم v6، تحويل استجابات `!trap`، وسياسة fallback في طبقة البيانات/حالات الاستخدام، لا داخل composables. تكون حالات الشاشة صريحة (تحميل، نجاح، فارغ، خطأ، نجاح جزئي). تبقى أسماء الأوامر وخصائصها وعمليات الصيانة الحساسة مغطاة باختبارات العميل الحقيقي ومحاكي RouterOS v6. أي دعم مستقبلي لـv7 يتطلب قرار منتج مستقلًا وإعادة اعتماد المسارات والأوامر والاختبارات قبل تفعيله.

## مسار انتقال معماري مقترح

1. **تثبيت العقود دون نقل سلوك:** إضافة عقود repository لحالات الاستخدام ذات المخاطر/الحدود الواضحة، بدءًا من AI Doctor وتنزيل النسخة الاحتياطية. تبقى التطبيقات الحالية متوافقة عبر adapters داخل الوحدة.
2. **فصل حالات الاستخدام:** نقل جمع snapshot التشخيصي وسياسة v6، ثم تنزيل النسخ وإدارة SAF، إلى Use Cases صغيرة ذات مدخل/نتيجة صريحة. لا تغيّر أوامر RouterOS في عملية الفصل.
3. **تخفيف ViewModel الرئيسي:** تجميع العمليات في واجهات feature-specific، مثل `RouterConnection`, `UserManager`, `Backups`, و`AiDoctor`, مع إبقاء `MikroTikViewModel` كواجهة توافق مؤقتة للشاشات القديمة.
4. **توحيد ملكية الحالة والتدفقات:** توحيد حزمة ViewModel، وإبقاء `StateFlow` في ViewModel، وجمعه بـ`collectAsStateWithLifecycle`. تم اعتماد هذا النمط في الشاشات التي تغيرت ضمن العمل الحالي، ولا يُقترح تحديث شامل غير مرتبط.
5. **استقلال الاختبارات:** وضع اختبارات نطاق لمنطق لا يحتاج Android، واختبارات adapters لـRoom/API. لكل أمر حساس اختبار نجاح، `!trap`، رفض صلاحية، وفشل جزئي على RouterOS v6. تشمل اختبارات النقل صيغ أطوال API المختلفة، بما فيها صيغة الخمسة بايت.
6. **تثبيت سياسة RouterOS:** البناء الحالي يقبل v6.x فقط. أزيل مسار REST من المستودع، وبقيت فروع أوامر v7 داخل User Manager معزولة خلف بوابة v6 فلا يمكن الوصول إليها. أي إعادة دعم مستقبلية تحتاج قرارًا واختبارات مستقلة.
7. **التقسيم إلى Gradle modules لاحقًا فقط:** يُنظر فيه بعد ثبات العقود وظهور حاجة بناء/تملك مستقلة؛ لا يُنصح بتقسيم واسع الآن لأنه يرفع مخاطر الرجوع ويصعب التحقق من التوافق.

كل مرحلة صغيرة وقابلة للتراجع، ويجب أن تمر باختبارات RouterOS v6 و`lintDebug` قبل الانتقال للمرحلة التالية.

## نتائج الأمان والتغييرات المنفذة

- **الأسرار في حالة السكون:** يستخدم التطبيق Android Keystore مع AES-GCM. أصبح `CryptoManager.encrypt` يفشل بأمان ويعيد `null` إذا تعذر التشفير بدل الرجوع إلى نص صريح. مسارات حفظ الراوتر وTelegram لا تحفظ قيمة سرية جديدة إذا تعذر تشفيرها؛ تعرض واجهة Telegram تحذيرًا، ويبلّغ ViewModel أن الاتصال قد نجح دون حفظ كلمة المرور محليًا.
- **بيانات قديمة:** `decrypt` ما زال يقبل القيم القديمة غير المشفرة للتوافق؛ لذلك قد تبقى أسرار سبق حفظها كنص صريح حتى تُعاد كتابتها. ينبغي إضافة ترحيل تدريجي مضبوط (من دون حذف بيانات أو تغيير مخطط Room) بعد اختبار استعادة البيانات، يشمل كلمات مرور الراوتر وتوكن Telegram وإعدادات AI Doctor. هذا قيد متبقٍ وليس ادعاءً بأن البيانات التاريخية مشفرة بالكامل.
- **حدود مشاركة الملفات:** كان FileProvider يتيح جذورًا واسعة من التخزين الخارجي والكاش. ضُيّق الآن إلى مجلدات `cache/previews`, `cache/exports`, `cache/designs` ومجلد `Download/` القديم فقط، ونُقلت ملفات معاينة PDF إلى المجلدات المقابلة. مزود FileProvider غير مصدّر ويستخدم URI grants.
- **النسخ الاحتياطي:** `allowBackup` ما زال مفعّلًا، لكن قواعد Android القديمة والحديثة تستبعد Room وSharedPreferences؛ هذا يمنع تضمين قواعد البيانات وتوكنات Telegram في النسخ المحددة. يلزم إبقاء ملفات القواعد متزامنة عند أي تغيير في مخازن الأسرار.
- **الشبكة:** إعداد TLS يثق بمخازن النظام ولا يستخدم trust-all. الاتصال المدعوم مع RouterOS v6 يستخدم Native API على 8728 أو API-SSL على 8729؛ كلاهما يحتاج شبكة موثوقة أو VPN. أزيل مسار REST/HTTP من المستودع، وأصبحت عمليات إعادة التشغيل والإيقاف وعمليات Hotspot تعتمد حصريًا على جلسة API أصلية أو تفشل برسالة صريحة. FTP غير مشفر بطبيعته؛ واجهة التنزيل تحذر من ذلك وتوصي بشبكة موثوقة/VPN.
- **المكونات:** شاشة الإطلاق فقط `exported=true` لكونها Launcher، وFileProvider `exported=false`. لم يُعثر على WebView أو JavaScript bridge في مسح المصدر الحالي. صلاحية التخزين العامة مقتصرة على أجهزة API 28 وما دون، والتنزيلات الحديثة تستخدم MediaStore/SAF.
- **الرصد:** أضيف `OperationTelemetry` محلي ومنظم بقوائم قيم ثابتة: أحداث ونتيجة/مدة/فئة خطأ/نقل/عائلة أمر/عدادات. لا يسجل مضيف الراوتر أو اسم مستخدمه أو كلمة مروره أو command/reply أو URL أو prompt أو response أو Telegram token/chat ID. أزيلت سجلات `Log.*` و`printStackTrace()` الخام من مصادر التطبيق التي راجعناها؛ الرصد يكتب إلى Logcat فقط ولا يرسل telemetry لخدمة خارجية.
- **الذكاء الاصطناعي:** إعدادات API والترويسات الحساسة محفوظة بالتشفير، وعنوان HTTP مسموح للخدمات المحلية/الخاصة فقط؛ لا تُمرر ترويسات الاعتماد عبر redirects، ويجب أن يبقى إرسال بيانات الراوتر إلى مزود خارجي واضحًا للمستخدم ومقصودًا.

## التحقق والقيود

- نجحت `:app:testDebugUnitTest`: **71 اختبارًا، صفر فشل** في وقت المراجعة الأصلية؛ يعاد تشغيلها بعد التغييرات.
- نجحت `:app:lintDebug`; بقيت تحذيرات deprecated/nullability موجودة في ملفات متفرقة، ولم تمنع المهمة.
- نجح `git diff --check` في آخر الفحوصات السابقة لتوثيق هذه المراجعة؛ يعاد قبل commit.
- لم يُنفذ بناء APK محليًا. بناء CI على GitHub هو خطوة التحقق التالية بناءً على طلب المستخدم.
- اختبارات المحاكاة تثبت سلوك العميل والمسارات المختبرة، ولا تثبت التشغيل على كل RouterBOARD أو كل patch release. يلزم اختبار ميداني لاحق على أجهزة فعلية RouterOS v6، خصوصًا User Manager وFTP والصلاحيات.
